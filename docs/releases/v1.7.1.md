# SL4A_TouchScreen v1.7.1

Patch release for the Gate5 production activation line.

## What changed

### Secure Boot activation recovery

`v1.7.0` correctly resolved the active DKMS signing identity during install,
but the separate `activate` path still carried an older hard-coded
`/var/lib/dkms/mok.pub` enrollment check. That is not correct for Ubuntu's
packaged DKMS, which normally uses:

```text
/var/lib/shim-signed/mok/MOK.priv
/var/lib/shim-signed/mok/MOK.der
```

`v1.7.1` makes `activate` use the same distro-aware DKMS identity resolution
as `install`, including `/etc/dkms/framework.conf` and
`/etc/dkms/framework.conf.d/*.conf` overrides.

This exact corrected path was rechecked on the qualified Surface Laptop 4 AMD
unit with Secure Boot enabled. The runtime check resolved:

```text
DKMS signing key path: /var/lib/shim-signed/mok/MOK.priv
DKMS MOK certificate path: /var/lib/shim-signed/mok/MOK.der
```

and completed with both AMDI0060 and MSHW0231 bound.

### Release/documentation audit

The current-facing README, docs and wiki were reconciled with the actual
qualified implementation:

- production SL4 multitouch is described as the **standard-transport CapImg
  path with the in-kernel CapImg multitouch tracker (input-quality beta)**;
- the legacy `--raw` transport remains explicitly diagnostic/research only;
- the tracker pipeline now documents the real ordering:
  **Hungarian assignment before post-association duplicate/coalescing**;
- Secure Boot guidance uses the active DKMS certificate path instead of
  assuming `/var/lib/dkms/mok.pub`;
- late-boot activation is consistently described as occurring after
  `multi-user.target`, not as a post-login service;
- the compatibility matrix distinguishes single-unit Gate5/Secure-Boot
  qualification from the still-unfinished broad E1 campaign.

## Qualification scope

Still qualified on one physical Surface Laptop 4 AMD / MSHW0231 unit, not a
broad hardware/firmware/kernel compatibility claim.

Input-quality qualification remains in progress for close-contact continuity,
crossing/identity retention, rapid lift/re-contact, 3/4/5 fingers, edge/corner
behavior, palm handling, stylus validation/coexistence, and broader hardware
coverage.

The separate fresh-MOK-enrollment flow (new certificate → firmware MOK Manager
enrollment → reboot) remains implemented but has not yet been independently
hardware-qualified.
